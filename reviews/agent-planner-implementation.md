# Task 3 native OAuth planner

The agent now has a single-turn CLI, private application OAuth, an experimental native structured planner, and a versioned model evaluation runner. The official Codex CLI probe in `a20243f` remains negative evidence about that separate route.

## Interfaces

- `python -m agent.auth login` prints a single PKCE authorization URL and listens at the registered localhost callback for up to five minutes. Open the emitted URL in the integrated browser. `python -m agent.auth status` returns file availability and integrity status without network traffic.
- The credential source uses a 0700 application directory in OS user data and a 0600 JSON credential file. It writes via a private temporary file, syncs it, atomically replaces the prior file, and syncs the directory. A nonblocking file lock spans login and each provider session, including proactive refresh and persistence. The provider is constructed with an explicit application credential source. The login command clears ambient proxy variables for the OAuth library's ephemeral token exchange. Inference and proactive refresh use a dedicated proxy-free TLS client with redirects disabled and exact HTTPS endpoint checks.
- `python -m agent.cli [gateway options] health` reports provider, credential file status and optional pinned release/catalog identity. Credential file status does not make a remote validity or subscription check.
- `python -m agent.cli [gateway options] ask --plan-only 'Qual o PL?'` prints the structured decision and canonical prompt, schema, catalog and decision SHA-256 values. Omit `--plan-only` to execute validated query intents through the existing gateway and render trusted results deterministically. Add `--explain` to a query execution to show the gateway's verified executed SQL from the same run. The CLI only retrieves this SQL for inspection. Clarifications and refusals come from fixed templates. Each question starts independently, so no prior filters carry into a new question. Multi-turn follow-ups such as A19 remain pending.
- `python -m agent.cli [gateway options] plan-file <intent.json>` executes a typed Decision without OAuth or a model call and visibly labels the deterministic mode. Use an unwrapped Decision object at the file root.
- `python -m agent.evals [gateway options] --limit 3 --execute` scores the first three development prompts and executes exact query decisions against available independent numeric oracles. Expanded or holdout runs require `--authorize-expanded` after reviewing small results. The default run is one repetition and prints a JSON report to stdout. Reports include the requested alias, returned identifier when available, reported token totals, measured request counts, elapsed milliseconds and provenance hashes. The remote service exposes an alias that can change over time and supplies no weights digest. Capture it to an operator-controlled local file when useful.

Gateway options for the sealed local baseline from the task worktree are:

../../.venv-agent/bin/python -m agent.cli \
  --release-root ../../baseline/releases --release-id cvm-linux-uat-v3 \
  --mf ../../compatibility/dbt-v2-metricflow/.venv-mf/bin/mf \

The first candidate is `gpt-6-luna`. The runner has no fallback. A candidate change requires an explicit code/config decision and separate evidence. The planner uses Pydantic AI 2.66.0 with strict `NativeOutput` around the discriminated Decision. It registers no tools and disables Pydantic AI instrumentation and both framework and SDK retries. An invalid structured response can trigger one clean repair request using a fixed instruction with no copy of the invalid output. The native provider's reactive 401 replay is blocked to preserve this budget. The CLI and gateway use one 60-second monotonic deadline per turn.

The inference client caps wire response data at 512 KiB and accepted structured text at 8 KiB. The client also rejects provider-reported output over 2,048 tokens per request, including reported reasoning tokens. This allowance accounts for the native reasoning model and supersedes the 512-token assumption in the earlier local-model notes. Codex drops generic maximum-output-token and temperature parameters. These client limits bound accepted output and streamed data. They do not impose a server-side token spending cap, and token enforcement depends on reported usage. Errors shown by the CLI contain bounded codes instead of raw responses or exception traces.

## Verification

- Initial auth, planner, CLI and eval test collections failed on their missing modules before implementation. The token limit regression subsequently failed with `invalid_model_output` when a large invalid response still triggered repair, then passed after adding the per-request usage guard.
- Four mocked native transport scenarios verify the exact Codex HTTPS path, application bearer injection, empty tool registration, strict native JSON output, streaming, disabled response storage, omission of ambient OpenAI organization and project headers, and one request on HTTP 400, 500 and 401. The successful streaming test supplies typed events through the real pinned provider and SDK. A separate FunctionModel test verifies a single clean repair.
- The final focused auth/planner/CLI/eval suite passed 15 tests. The final full agent run against the sealed baseline passed 52 tests in 44.26 seconds. A deterministic CLI run with `--explain` returned April net flow of BRL 1,226,480,088.40, 1,196/1,200 reports and the verified executed SQL. The Python 3.12 hashed lock checked all 32 packages. The nine distinct numeric oracle families were replayed through the real gateway successfully. That replay used frozen decisions and contributes no model trials.
- The evaluation data contains 24 development and 16 holdout families with three independently written language variants per family. Dataset version 1 freezes the bytes separately. Development SHA-256 is `02ce841b61fc5494cf28e19d3af4ddbdf96b6acfef6e24212cc221661f0b7b72` and holdout SHA-256 is `b149481662e810cc1e33566ca002fb74947e10242bb063e77c6426aec1c26337`. The loader checks split identity, SHA-256, policy and clock. Reports count exact intents, supported intents, critical cases and available numeric oracles separately. Numeric oracles use the published CVM oracles and the sealed missing report/count evidence. The extra May class gap was independently confirmed by selecting `entity_id, report_date, reported, expected` from read-only `fct_daily` for rows with `reported < expected`.
- The parent operator reported fresh OAuth consent succeeded with `credentials_present`. One live `gpt-6-luna` compatibility canary on `Qual o PL?` returned `clarify/missing_period` with `[period]` in one attempt, exit 0. This canary ran before the timing and served-model fields were available. The parent operator owns subsequent bounded development review.

## Remaining acceptance

The runner's current nine numeric oracle families are a subset of the planned end-to-end suite. Additional independent numeric goldens, hidden-value fixtures, multi-turn follow-up qualification, the full reviewed holdout run, resource/latency evidence and independent delivery review remain open. The checked-in holdout is a frozen first version and should be evaluated only after development choices are fixed. If any holdout is used for tuning, version and replace that holdout before a new acceptance claim. Health, deterministic results, OAuth consent, and mocked wire evidence do not establish natural-language accuracy or local production acceptance.
